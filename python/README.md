# IPM synRM: the Python code

This folder holds the Python code of an open-source motor-design project: a 36-slot, 8-pole permanent-magnet-assisted
synchronous reluctance motor (IPM synRM). It is the pipeline that draws, solves, optimizes and checks the motor. Python
draws the geometry (`motorgeo`), FEMM 5.0 solves it, optimizers search it, and CalculiX, Elmer, ROSS and SALib verify it,
along with studies of copper losses, windings and heat.

The code is written to be read. Most modules open with a docstring that explains the method, says how to run the file and
what numbers to expect; this README is a guide to those docstrings, grouped by purpose.

It runs on one Windows PC with FEMM 5.0 and [uv](https://docs.astral.sh/uv/). Every program and folder of that PC is named
in [`config.toml`](config.toml), which holds the paths of the PC the code was developed on; a per-machine configuration
is planned.

## Setup and running

Requirements: Windows, FEMM 5.0 and uv. The tool checks, the test bench and the stress and thermal checks also use
CalculiX, Elmer, PrePoMax and MATLAB (programs named in `config.toml`) and ROSS (in an environment of its own); the Gmsh
Python package and the other libraries come with the environment.

From this folder, in PowerShell:

```
uv sync                          # makes .venv and installs the exact versions in uv.lock
uv run python paths.py           # lists every tool and folder in config.toml; says which program it cannot find
uv run python <script>           # runs any script of this folder with that environment
```

- The environment pins Python 3.13, numpy 2.5.4, scipy 1.18.1, pandas 3.0.6, matplotlib 3.11.2, shapely 2.2.0,
  ezdxf 1.4.5, gmsh 4.15.2, pymoo 0.6.2 and SALib 1.6.0 ([`pyproject.toml`](pyproject.toml), [`uv.lock`](uv.lock)).
  ROSS 3.1.0 is not among them: it pulls in many more packages, so it lives in an environment of its own,
  [`envs/ross`](envs/ross), which `check_tools.py` uses through that environment's python.
- FEMM 5.0 has its own Python binding, `pyfemm-qt` (`import femm`), which talks to FEMM over TCP. `pyproject.toml` links it
  from `D:/Apps/femm-qt/pyfemm`, so FEMM 5.0 must be installed there, or that line changed. It is the one machine path
  outside `config.toml`, because uv reads that file and not the code.
- The numbers quoted in the docstrings and in this guide are FEMM 5.0's (FEMM 5.0.20261101, build 1144, with Python
  3.13.16, run on 2026-11-04 unless a docstring gives another date).
- Scripts write into `out/` (and `runs/` for `evaluate.py`). Both folders are git-ignored; everything in them is
  regenerated by running the scripts again.
- The small teaching scripts in [`learn/`](learn) are run from inside that folder; several modules of
  [`optimization/`](optimization) are run as modules from this one, for example
  `uv run python -m optimization.thermal_fem`. Each docstring gives its own command, and the tables below repeat it.

## Tests

```
uv run pytest -m "not femm"      # the tests that need no FEMM
uv run pytest                    # all tests; the ones marked femm start real FEMM 5.0 processes
```

The tests marked `femm` (21 of them) need FEMM 5.0 and leave nothing running; `tests/conftest.py` quits any FEMM that a
failing test left behind. The others use stand-in processes, made-up data and the real files of this folder, and start no
solver.

**Many tests check the studies' stored results, which the repository does not carry.** They read the results that the studies
write into `out/` (the optimized design, the flux and iron-loss maps, the flux-explorer sweep) and FEMM 4.2's reference outputs
(`femm42-out/`). `out/` is git-ignored and `femm42-out/` is kept outside the repository, so in a fresh clone those tests fail or are
skipped until the studies have run. The table in [section 11](#11-the-tests) names the modules.

Several modules also pin the wording of docstrings and of this README (for example the rows for `bench/` and for
`rulings.py` + `stale.py` in the guide below, and the exit statuses of `check_tools.py`), so a change to those texts shows up as a
test failure.

## Where the tool paths live

[`config.toml`](config.toml) is the one place that names this PC's programs and folders, and [`paths.py`](paths.py) reads it.
No script types a drive path: a script asks for a name, and `tests/test_paths.py` fails if one holds a path of its own.

```
[tools]   femm (FEMM 5.0's folder), ccx, cgx, gmsh, prepomax, elmer, elmergrid, matlab: the programs
[paths]   out, rulings, femm42_out, reference_fem, simulink_plant, motor_structure_mat, dxf_rotor, dxf_rotor_with_band,
          dxf_stator, femm_matlib, docs_figures (the repository's docs/figures): folders and files
[femm]    workers = 8, priority = 'below_normal'
```

```python
import paths
paths.tool("gmsh")                # the program, as a Path; FileNotFoundError naming "gmsh" if it is not there
paths.path("out")                 # a folder or file; a relative entry starts at this folder
paths.setting("femm", "workers")  # a plain value, here the number 8
```

The paths in `config.toml` are those of the PC the code was developed on; a per-machine configuration file is planned, so that
the shared file need not carry one PC's paths. Until then, to change where a program lives, edit its line in `config.toml`
(write a Windows path in single quotes, which keeps the backslashes literal), then run `uv run python paths.py`. It ends with `8 of 8 tools found` when every program is there
(exit status 1 and a `MISSING` row if one is not).

## How heavy runs are organized

One heavy run at a time on the PC: two at once only slow each other down and make the desktop stutter. The code written
for this rule (the bench, `check_tools.py`, `check_queue.py`, the optimization modules) goes through
[`femm_queue.py`](femm_queue.py). It takes one machine-wide slot first (a lock on a file under `out/.femm/`), runs at
below-normal priority under a timeout, runs at most 8 workers or threads (`[femm] workers` in `config.toml`), and ends only
the processes it started itself. `uv run python femm_queue.py` says who holds the slot.

Scripts that start their own FEMMs without taking the slot: `barrier_study.py`, `reference_open.py`, `validate_full.py`,
`optimize_demo.py`, `worker_scaling.py`, `mesh_study.py`, `evaluate.py`, `example.py`, `check_femm.py`,
`validate_fix_zeros.py`, `validation/mesh_checks.py`, `validation/m19_femm5.py` and `validation/run_all.py`, which runs
most of them in turn. Run one of them only while nothing else heavy runs.

## Guide to the files

Eleven groups, by purpose. Each table gives, for every file, what it does and how, the command that runs it, and the
headline result where the docstring states one.

### 1. The core

The core is the code that every other script in the folder builds on: the geometry kernel and its writers, the start-up of one private FEMM 5.0 per process, the machine-wide solver slot with its pool of FEMM workers, a reader for FEMM's text files, the file that names the PC's programs and folders, and the bookkeeping that marks stale results. `example.py` at the end runs the chain on one screen. Commands are run from the folder `python/`.

| File | What it does, and how | Run | Result |
|---|---|---|---|
| `motorgeo.py` | The geometry kernel: the cross-section is Python data (lines, arcs, regions) and every tool is a writer. `Params` holds the dimensions (baseline: the hand-drawn `reference/IPM synRM analysis.FEM`, except values marked PLACEHOLDER), `build()` draws one symmetric sector, `check()` flags thin ribs and bridges before any solver runs, `to_femm`, `to_dxf` and `to_gmsh` write the files, and `FemmModel` solves rotor positions. | | |
| `paths.py` + `config.toml` | [config.toml](config.toml) is the one place that names the PC's programs (`[tools]`: FEMM, CalculiX, Gmsh, PrePoMax, Elmer, MATLAB), folders (`[paths]`) and FEMM limits (`[femm]`: 8 workers, below-normal priority). `paths.py` reads it with `tool(name)`, `path(name)` and `setting(section, key)`, so no script types a drive path; a program that moved raises an error naming the line to correct. | `uv run python paths.py [other_config.toml]` | lists every name with its path, then `8 of 8 tools found`, exit status 0 (1 if a tool is missing) |
| `femm_session.py` | One private FEMM 5.0 per Python process. `open_femm()` starts a hidden FEMM on a free port of its own (not the 48015 that an interactive FEMM window answers on) at below-normal priority, set before the start so that FEMM inherits it, and points the `femm.mi_*()` and `femm.mo_*()` calls at it; `close_femm()` quits it. ### 2. The first studies

The scripts that use FEMM do not take the solver slot of [femm_queue.py](femm_queue.py), so only one of them should run at a time; outputs go to the git-ignored folders `out/` and `runs/`.

#### The validation/ folder (FEMM 5.0 against FEMM 4.2)

### 7. The optimization study

The study looks, on the band-free motor (the rotor without the air band behind each magnet, `motorgeo.Params(barrier="none")`, and the stator around it), for the geometries where the torque cannot rise any more without the ripple rising too: the Pareto front of mean torque against torque ripple at the scoring point, inside a fixed envelope (radii, air gap, shaft, stack and the bought magnets' size). Every file is driven from one black box, `optimization/design.py`, and the table follows the order of the study (check, sweeps, screening, optimizer runs, cross-check, fine-mesh re-score, DXF export, side-by-side figure). Each file is run from `python/` as a module; FEMM is started only through `femm_queue.femm_pool` (one heavy run at a time), and results go to `out/optimization/<step>/` (git-ignored).

### 8. The rotor stress check

The optimizer thinned the two strips that hold each pole's outer steel and its magnets against the centrifugal pull (the centre rib to 1.0 mm against 3.3 mm on the reference, the outer bridges to 1.4 mm against 1.56 mm), and the bridge guard and the rib floor are manufacturing limits, not strength limits. `optimization/stress_ccx.py` therefore puts the optimized rotor through the bench's centrifugal-load case in CalculiX and reports stress only (the electromagnetic cost of a wider rib or bridge is not in it). The strength limits it uses are placeholders: the maker's sheet skips the mechanics of the lamination steel M-19, so they come from a neighbouring grade and similar grades.

### 9. Copper losses with the proximity effect, and the winding studies

#### The copper losses (skin and proximity effect)

The first winding study (`optimization/winding.py`) priced the winding's AC loss with one low-frequency proximity formula and found it negligible at 3,000 rpm; these files test that formula strand by strand against FEMM and follow R_ac / R_dc (the AC resistance over the DC one) from the fundamental up to the PWM switching frequency, and the loss over the whole speed range. `ac_theory.py` holds the exact results for round wires and `ac_calibration.py` tests FEMM's time-harmonic solver against them; `ac_slot.py` draws one slot strand by strand (studies in `ac_slot_study.py`), `ac_machine.py` takes the machine's own field at the copper from magnetostatic solves of the sector, `ac_pwm.py` derives the inverter's ripple current, and `copper_loss.py` adds these up as one fast function that `copper_loss_study.py` checks against the slot solves. ### 11. The tests

The tests are run from `python/` with pytest and, like the code, assume Windows. `uv run pytest -m "not femm"` runs the suite without starting FEMM: the tests marked `femm` start real FEMM 5.0 processes, but the fixtures in conftest.py import `femm_session`, and with it FEMM 5.0's Python binding, for every test, so the binding must still be installed. In the table, Needs gives the number of tests marked `femm`, or says `results in out/` where tests read files that earlier runs of the studies wrote under `out/`, which is not part of the repository (the optimized design `out/optimization/final/final.json` and the flux and iron-loss maps in `out/optimization/maps/chosen/`); counts are test functions. `test_paths.py` and parts of the B4 and B5 bench tests also expect the programs named in `config.toml` to be installed. Several modules pin the wording of docstrings and of the README, so a change to those texts shows up as a test failure.

## What is not in this folder

- **The built flux page and v2.** The interactive flux page, `pages/Rotor Flux Explorer.html` (about 17 MB), is not in this folder, and v2 of
  the page is published separately. This folder holds the v1 generator (`flux_explorer_sweep.py`, `flux_explorer_sweep120.py`,
  `flux_explorer_build.py`, `flux_explorer_template.html`); `validation/compare.py` checks the built page when it is there and reports it
  missing otherwise.
- **FEMM 4.2's reference outputs** (`femm42-out/`, 1.2 GB, with its SHA-256 list) are kept outside the repository.
  `validation/compare.py`, `validation/mesh_checks.py` and `validation/provenance.py` read them, `config.toml` names the folder
  (`femm42_out`), and `tests/test_paths.py` expects it to exist.
- **The MATLAB flux-map files** (`matlab/maps/`) are published later, with their write-up; `optimization/maps_matlab.py` writes
  `matlab/maps/fem_maps.mat` and reads it back.
- **The results of the studies** (`out/`) are git-ignored and not in the repository: the optimized design
  (`out/optimization/final/final.json`), the flux and iron-loss maps (`out/optimization/maps/chosen/`), the flux-explorer sweep and the
  other outputs the studies write. The thermal, winding, copper-loss, short-circuit and motor-map code and many tests read them; in a
  fresh clone those tests fail or are skipped until the studies have run ([section 11](#11-the-tests) names the modules).
